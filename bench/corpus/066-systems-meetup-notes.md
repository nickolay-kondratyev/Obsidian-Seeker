Notes from the local systems programming meetup, held at a coworking space downtown. Roughly thirty people attended, a mix of embedded folks, a couple of game engine developers, and several people like me still early in learning Rust seriously for the first time outside of toy examples. The evening had two talks and an open discussion period afterward, plus informal networking over pizza before the formal program started around seven. I went mostly to hear the second talk on memory layout, but the first one turned out to be more directly useful for my current todo app project than I expected walking in, especially the parts about error handling patterns that map almost directly onto the `TodoError` enum I've been building at home.

## Talk one: error handling patterns in real Rust codebases

The first speaker works on a mid-sized networking tool and walked through how their error handling evolved over roughly two years of production use, starting from scattered `unwrap()` calls in early prototypes through to a structured system today. Early on, they used `unwrap()` everywhere, which is fine for prototypes but caused actual production panics once the tool started running unattended on customer infrastructure. They moved to `Result<T, String>` next, which was better but made it hard to match on specific error variants at call sites, forcing string comparisons that felt fragile and broke silently whenever someone tweaked an error message for clarity. Eventually they settled on a layered approach: leaf-level errors as small enums specific to each module, wrapped into a top-level application error using the `thiserror` crate for boilerplate reduction, with `anyhow` reserved specifically for `main` and other top-level boundaries where callers don't need to match on specific variants anymore, just report and exit. The live demo showed how `#[from]` attributes in `thiserror` auto-generate `From` implementations, which cut a noticeable amount of manual boilerplate compared to the hand-written conversions they used to maintain. Someone asked about performance overhead of boxing errors, and the answer was essentially "measure before you worry about it," since error paths are rarely hot paths in most real-world systems and premature optimization here mostly just adds unnecessary complexity for no measurable benefit anyone has actually observed in practice. Someone else pushed back gently, pointing out that boxed trait objects do add an indirection cost worth knowing about even if it rarely matters, and the speaker agreed that's a fair caveat worth keeping in the back of your mind for genuinely hot loops.

## Talk two: memory layout and why it matters even without unsafe code

This was the one I came for, and it delivered. The speaker, an embedded developer who spends most of her time on resource-constrained microcontrollers, walked through how Rust structs get laid out in memory and why field ordering can matter for size even when you're not writing a single line of unsafe code anywhere in your program. She demoed `std::mem::size_of` on a few struct variants, showing how reordering fields from largest to smallest can shrink a struct significantly due to alignment padding the compiler has to insert between misaligned fields to satisfy hardware requirements. A `struct` with a `bool`, then a `u64`, then another `bool` pads out substantially larger than the same three fields reordered with the `u64` first and both bools packed together at the end, because the compiler has to insert padding to keep the `u64` aligned to an eight-byte boundary regardless of what surrounds it. She also covered `#[repr(C)]` versus Rust's default representation, and when you'd actually reach for the C-compatible layout, mainly FFI boundaries and certain hardware register mapping scenarios where the exact byte layout has to match a spec you don't control. The audience got noticeably more engaged once she pulled up `cargo bloat` output showing real size numbers on an actual embedded firmware binary rather than talking in the abstract about theoretical alignment rules, since seeing fifteen percent shaved off firmware size from pure field reordering made the abstract padding discussion suddenly feel very concrete and worth caring about for my own future projects, even the small hobby ones I'm building right now that will probably never run on constrained hardware at all. She closed by mentioning that the compiler will actually reorder fields for you automatically in the default representation, and the manual reordering demo was mostly to build intuition for reading `cargo bloat` output later, not something you need to do by hand in everyday code most of the time. Someone in the front row asked whether this kind of optimization was worth chasing on desktop applications at all, and she was refreshingly honest that for most desktop-class programs it simply isn't, memory is cheap there and engineering time is much better spent elsewhere.

## Open discussion

Q&A ran long, past the scheduled end time, because people kept asking follow-ups about tooling. Someone asked about `miri` for catching undefined behavior in unsafe code during testing, which neither speaker used regularly but both agreed was worth adopting given how it catches real classes of bugs that regular tests miss entirely, especially around aliasing violations that are otherwise nearly impossible to spot through manual code review alone. There was a good tangent about when learning embedded Rust makes sense versus staying on desktop or server-side work first, general consensus was: get comfortable with ownership and the borrow checker on desktop where the feedback loop is fast and debugging tools are mature, then move to embedded once those fundamentals stop requiring conscious thought during every single line you write, since embedded adds its own substantial layer of complexity on top that's much harder to absorb while still fighting the basics of the language itself. Someone from the back asked about job prospects specifically, wondering whether learning Rust for systems work actually translates into hireable skills locally, and the responses were mixed but generally optimistic, with a couple of attendees mentioning their own companies had quietly started requiring or at least strongly preferring Rust experience for new infrastructure roles opening up over the past year. One person mentioned a compiler team is actively hiring and specifically wants people comfortable with the borrow checker's error messages, which got a laugh from most of the room given how many of us are still googling those same messages weekly.

## Takeaways for my own projects

Two direct actions for the todo app: adopt `thiserror` instead of my fully hand-rolled `TodoError` enum, since the boilerplate reduction looked meaningful even for a project this small, and it's a good excuse to learn the crate properly on low-stakes code before I need it somewhere that actually matters. Also want to run `cargo bloat` on the todo app just out of curiosity, even though binary size genuinely doesn't matter for a CLI tool I run maybe five times a day on my own laptop, purely because the demo made me want to see what my own struct layouts actually look like under the hood.
