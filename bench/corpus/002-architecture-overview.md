This document describes the current architecture of Ledgerline, our small-business invoicing web app. It exists so new contributors (and future us) don't have to reverse-engineer decisions from commit history. The stack is TypeScript end to end: a Node/Express API, a React frontend, and Postgres for storage. We keep the surface area small on purpose — one deployable API, one deployable frontend, no microservices — because a four-person team cannot afford the operational overhead of anything fancier right now. See [[007-database-schema-doc]] for schema details.

## System Overview

The API is a single Express service exposing REST endpoints under `/api/v1`. Authentication uses signed JWT cookies with a 30-minute access token and a 14-day refresh token, both httpOnly. The frontend is a Vite-built React SPA that talks to the API over HTTPS and never touches Postgres directly. Background jobs — recurring invoice generation, overdue-payment reminder emails, and nightly ledger reconciliation — run through a small job queue backed by a `jobs` table rather than a separate broker, since our volume doesn't justify Redis or SQS yet. Dana owns the API and job queue; Priyam owns the frontend; Kofi owns infrastructure and CI/CD; Lotte owns product scope and UX decisions that ripple into architecture, like multi-currency support.

## Data Model

Core entities are `organizations`, `users`, `customers`, `invoices`, `invoice_line_items`, `ledger_entries`, and `payments`. Every table except `organizations` carries an `org_id` foreign key, and every query is scoped by it at the application layer — there's no row-level security in Postgres yet, which is a known risk tracked as a follow-up. Invoices are immutable once sent: editing a sent invoice creates a new draft revision instead of mutating the original row, so that customers never see a total change silently under them. Ledger entries are append-only and double-entry style, debit and credit columns on every row, which makes reconciliation and audit trails straightforward even though it costs us some query complexity. Money is stored as integer cents in a `bigint` column, never as `float` or `numeric` with implicit rounding, to avoid the classic invoicing bug where totals drift by a cent after several edits. Timezones are stored per organization and used only for display; all timestamps in the database are UTC. Soft deletes are avoided — customers and invoices carry a `status` column instead, and rows are never physically removed except by an explicit, logged export-and-erase flow Kofi built for one enterprise customer.

## Deployment

The API and frontend deploy independently on every merge to `main` via GitHub Actions, with the API going to a small managed container host and the frontend to static hosting behind a CDN. Postgres runs as a managed instance with daily snapshots and point-in-time recovery enabled. Staging mirrors production topology but at a fraction of the size.

## Open Questions

A few architectural questions remain unresolved. Should we add row-level security in Postgres to enforce org isolation at the database layer, removing reliance on application code getting the `org_id` filter right every time? Kofi is cautiously in favor; Dana worries about the added complexity in local development and test setup. Separately, as we add multi-currency invoices, do exchange-rate snapshots belong on the invoice row itself or in a dedicated `fx_rates` table keyed by date? Lotte wants an answer before the multi-currency work starts next quarter, and Dana has a rough proposal sketched in [[017-api-design-doc]] that the team still needs to review together. There's also an open question about whether the job queue table will scale past a few thousand pending jobs, or whether we'll need a real broker sooner than planned.
