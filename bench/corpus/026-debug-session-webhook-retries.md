Ad-hoc debugging session, 2026-05-19, triggered by three duplicate payment-confirmation emails going out to one customer overnight. Attendees: Dana, Kofi (Priyam and Lotte looped in via async updates, not present live). Called by Kofi at 9am after the overnight alert queue showed the same webhook event processed three separate times against the same invoice, which shouldn't be possible given the idempotency key we added after the incident documented in [[016-incident-postmortem-payment-webhook]]. Dana joined immediately given the overlap with that earlier incident, and both wanted to rule out a regression before anything else, since a repeat of the same class of bug this soon would be a genuinely bad sign about whether the original fix actually addressed the root cause or just papered over the specific symptom we saw last time.

## Reproducing the issue

Kofi pulled the raw webhook payloads from the provider's dashboard first, confirming there were indeed three separate delivery attempts for the same event ID, `evt_9f2a1c`, roughly ninety seconds apart. That ninety-second spacing matched the provider's documented retry backoff exactly, which meant our endpoint was returning something other than a clean 200 on the first two attempts, causing legitimate retries rather than a bug on the provider's side. Dana grepped the API logs for the event ID and found the first attempt had actually succeeded internally, updating the invoice status and inserting the ledger entry correctly, but the response to the provider had timed out before it left our server, at four point eight seconds against a five-second timeout the provider enforces. The provider, seeing no response within its own timeout window, correctly retried, and our idempotency check — which looks up the event ID in a `processed_webhook_events` table before doing any work — should have caught the second attempt and short-circuited before touching the invoice again. It didn't, and that became the actual mystery worth chasing rather than the slow response itself, which was really just what surfaced the pre-existing gap in the idempotency logic. Kofi also pulled up the third delivery attempt out of caution, confirming it hit the API ninety seconds after the second, and by that point the invoice had already been updated twice, so the customer's invoice detail page briefly showed a total that didn't match either write cleanly. Dana flagged that this discrepancy alone would eventually have surfaced through a support ticket, so treating this as a near-miss rather than a full incident felt like the right framing.

## Finding the root cause

Dana added targeted logging around the idempotency check and re-triggered a test event locally against the same code path. The check was querying `processed_webhook_events` for the event ID, but the insert that records a newly processed event only happened after the invoice and ledger writes completed — meaning there was a window, exactly the four point eight seconds the first attempt was slow, where the idempotency row didn't exist yet even though processing was already underway. The second delivery attempt landed inside that window, found no matching row, and reprocessed the event as if it were new, which is precisely the kind of race condition that's rare enough to pass every test we've written but real enough to happen the moment production load introduces any meaningful latency into the response path. Kofi confirmed this by checking timestamps: the `processed_webhook_events` insert for the first attempt happened at 03:14:22.891, and the second attempt's duplicate-check query ran at 03:14:22.340, well before that insert landed. The third attempt succeeded in being correctly rejected only because by then the first attempt's insert had finally committed, closing the window. Dana pointed out this is a textbook check-then-act race, and the fix isn't more logging or a longer timeout, it's moving the idempotency claim to the very start of request handling rather than the end, ideally as an atomic insert-or-conflict against the database rather than a separate check-then-insert pair of statements that can interleave with a concurrent request. Kofi asked whether a longer provider timeout would have masked the symptom without fixing the underlying race, and both agreed it would have, which made them slightly uneasy about how long this exact bug could have sat latent under normal, faster response times before ever surfacing this visibly to a customer. They also discussed briefly whether increasing the timeout on our side, to give slow requests more room, was worth doing regardless of the idempotency fix, and decided it was — a five-second timeout on a provider webhook is uncomfortably tight given how variable database write latency can be under real load, especially once background jobs are competing for the same connection pool during a busy morning.

## The fix

```ts
async function claimWebhookEvent(eventId: string): Promise<boolean> {
  const result = await db.query(
    `insert into processed_webhook_events (event_id, claimed_at)
     values ($1, now())
     on conflict (event_id) do nothing
     returning event_id`,
    [eventId]
  );
  return result.rowCount === 1; // true = we claimed it, false = already claimed
}
```

Dana wrote this as a single atomic insert with an `on conflict do nothing`, claiming the event ID before any invoice or ledger work starts rather than after. If the claim fails, the handler returns 200 immediately without reprocessing, since a failed claim means either genuine duplicate delivery or a concurrent request already handling the same event, and both cases warrant the identical response. Kofi reviewed it, agreed it closes the race entirely rather than narrowing the window, and the two paired to add a regression test that simulates two concurrent requests for the same event ID hitting the endpoint within milliseconds of each other, confirming exactly one succeeds in claiming it. They also renamed the table's column from a vague `created_at` to `claimed_at`, on the theory that the old name quietly implied a record-after-the-fact pattern, which is exactly the assumption that caused the bug in the first place, and a clearer name might make the same mistake harder for someone to reintroduce later without noticing. Kofi suggested adding a short code comment above the query explaining why the insert happens first, not as documentation for its own sake but specifically so a future refactor doesn't accidentally reorder it back to a check-then-insert shape for the sake of readability, which is exactly the kind of well-intentioned cleanup that could silently reopen this precise race condition months from now.
