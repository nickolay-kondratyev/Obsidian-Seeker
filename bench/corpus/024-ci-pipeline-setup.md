This is the setup guide for Ledgerline's CI pipeline on GitHub Actions, covering how the workflow is structured and why, so the next person adjusting it doesn't have to reverse-engineer the YAML from scratch under deadline pressure. It assumes familiarity with the local dev setup in [[004-local-dev-setup]] and the testing approach in [[022-testing-strategy]].

## Full walkthrough

The pipeline lives in `.github/workflows/ci.yml` and runs on every push to a pull request branch and again on merge to `main`. It's a single workflow file with four jobs: `lint`, `typecheck`, `test`, and `build`, run in parallel rather than sequentially, since none of them depend on each other's output and running them together cuts total pipeline time roughly in half compared to our first attempt, which chained everything into one long job out of laziness more than any real reasoning.

The `lint` job runs ESLint across both `packages/api` and `packages/web` with `pnpm lint`, using the shared config in `packages/shared/eslint-config` so both packages enforce identical rules rather than drifting apart over time as different people touch different parts of the codebase. It fails the build on any warning, not just errors, which was a deliberate and slightly controversial choice Kofi pushed for — the reasoning being that an unaddressed warning today is a broken window that makes the next one easier to ignore, and in practice this has kept the warning count at exactly zero since the rule went in, rather than slowly creeping up the way it did before.

The `typecheck` job runs `tsc --noEmit` across the whole monorepo using the root `tsconfig.json`'s project references, which checks that `packages/shared`'s types resolve correctly for both consumers without actually emitting any JavaScript. This job catches an entire category of bugs before they ever reach a human reviewer — mismatched types between the API response shape and what the frontend expects, mostly — and it's saved us from shipping at least one broken deploy that would have otherwise only surfaced when a real user hit a specific screen.

The `test` job is the slowest of the four, since it needs a real Postgres instance for the integration suite described in [[022-testing-strategy]]. We use the `postgres:16` service container built into GitHub Actions rather than Docker Compose here, configured with a throwaway password and mapped to port 5432 inside the job's network namespace. The job waits for Postgres to report healthy using the built-in service health check before running migrations and then the full test suite. We cache `node_modules` between runs keyed on the `pnpm-lock.yaml` hash, which shaves close to ninety seconds off average job time, though the cache occasionally goes stale in ways that are annoying enough to debug that Kofi's added a `workflow_dispatch` input to force a clean run when needed without having to touch the lockfile just to invalidate a cache key.

The `build` job runs `pnpm build` for both packages, producing the compiled API bundle and the static frontend assets, and uploads both as workflow artifacts. This job doesn't deploy anything by itself — deployment is a separate workflow triggered only on merge to `main`, described in [[009-deploy-to-staging]] for the staging half of that flow — but having a successful build artifact on every pull request means we catch build-breaking changes before they ever get anywhere near a deploy, rather than discovering a build failure at the worst possible moment during an actual release.

All four jobs must pass before a pull request can merge; this is enforced as a required status check in the repository's branch protection rules, and nobody on the team has bypass permissions configured, including Dana, which was a deliberate decision made early on specifically to remove the temptation to skip the gate under deadline pressure. If a job fails, the PR page links directly to the failing step's logs, and re-running just the failed job — rather than the whole pipeline — is usually enough once the underlying issue is fixed, which keeps iteration reasonably fast even when something needs a few attempts to get green. Average total pipeline time right now sits around four minutes for a typical pull request, which the team considers acceptable, though Kofi keeps a loose eye on it creeping upward as the test suite grows and has floated splitting the integration suite further if it ever crosses the ten-minute mark, since past that point people start reflexively context-switching away and losing the tight feedback loop that makes the whole gate worth having in the first place.

## Troubleshooting a red pipeline

If a job is red and the cause isn't obvious from the logs, check whether the `pnpm-lock.yaml` cache went stale first — a `workflow_dispatch` run with the force-clean input usually rules that out in under a minute. If `test` fails only in CI and not locally, it's almost always the Postgres service container starting slower than expected; re-running the job alone usually resolves it. For genuinely new failures, the failing step's log links straight from the pull request, so start there before assuming your code is at fault.
