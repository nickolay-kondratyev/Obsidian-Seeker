We picked Postgres for Ledgerline in the earliest planning sessions and I still get asked why every few months, usually from someone who liked Mongo for rapid prototyping elsewhere, so I'm writing the argument down once instead of re-litigating it from memory in Slack each time. The short version is that an invoicing product is fundamentally a relational domain: invoices belong to customers, customers belong to organizations, line items belong to invoices, payments reference invoices, and ledger entries reference all of the above while also needing to be queried in aggregate for account balances. Every one of those relationships is a foreign key in the classical sense, and every meaningful query we've written since launch — unpaid invoices for a customer, ledger entries summed for an account this month, invoices whose total doesn't match their line items — is a join or an aggregate, the exact query shapes a relational database is built to make fast and correct. A document database can model these relationships too, but it does so by either denormalizing data across documents, which creates update-consistency problems the moment an invoice needs its total recalculated after a line item changes, or by doing manual application-side joins, which is slower and more error-prone than letting the database enforce it. We looked hard at whether Mongo's flexible schema would have bought us meaningful speed in the first few weeks, since that's the pitch — no migrations, just start writing documents — and concluded it would have cost us more than it saved, because the schema wasn't actually unclear to us. We knew from the first planning doc that invoices have line items, that money needs to be exact, and that ledger entries are append-only double-entry records; the ambiguity document databases help you defer simply didn't exist in our case. The flexibility Mongo sells is most valuable when you genuinely don't know your data shape yet, and we did, almost completely, before writing a line of schema.

## the money problem specifically

The clearest argument, honestly, is money. Storing `total_cents` as an indexed bigint column with a `CHECK` constraint that it's non-negative is trivial in Postgres and enforced at the database layer, so no application bug can ever write a negative invoice total even if someone forgets to validate it in the API layer. Mongo would let us store money as whatever we wanted in a document — a float, a string, an object with currency and amount — with the correctness resting entirely on application discipline instead of the database itself refusing bad data, and application discipline is exactly the thing that erodes under deadline pressure, which invoicing software reliably runs into. There's also the transactions angle: a paid invoice's status update, ledger entries, and payment record either all commit or none do, by default in Postgres.

## what we'd give up

To be fair to the other side, Postgres does cost us some things Mongo would have made easier. Horizontal write scaling is genuinely harder — we'd need read replicas and eventually partitioning strategies well before Mongo's sharding would become necessary at our current scale, though we're nowhere near that ceiling yet with a few hundred organizations. Schema migrations, covered in [[014-writing-db-migrations]], require actual planning and sometimes downtime windows for large tables, where Mongo would have let us just start writing a new field and let the app handle absence gracefully. And full-text search, if we ever build the "search all your invoices" feature Lotte keeps mentioning in roadmap discussions, would need `pg_trgm` or an external search service, whereas Mongo has decent text search built in without extra infrastructure. None of these costs are hypothetical — Kofi has already flagged migration-planning overhead as real friction on the ops side, and the write-scaling ceiling, while distant, is worth revisiting honestly once organization count grows past a few thousand rather than assumed away forever.

## the counterfactual that convinced me

I tried, mostly as an exercise after one of these Slack debates got heated, to actually sketch what the Mongo schema would look like for just the invoice-and-ledger slice of the product, and it kept wanting to become relational anyway — I found myself drawing arrows between documents, which is just a foreign key with extra steps and none of the referential integrity enforcement. Once I noticed I was reinventing joins by hand and hoping the application layer respected them consistently, the decision stopped feeling like a debate and started feeling obvious, the same way it apparently felt obvious to Dana and Kofi from the very first architecture conversation before I'd even joined the team, per [[003-dana-dev-journal-kickoff]]. That exercise is honestly the thing I'd point anyone to now instead of re-explaining the abstract argument again — draw your actual domain's document shapes out by hand and see how fast the arrows between them start looking exactly like the relationships you were trying to avoid formalizing, because for us they showed up within about fifteen minutes of trying. I still have the notebook page from that afternoon, three boxes labeled invoice, customer, and ledger_entry with arrows scrawled between them in blue pen, and a fourth box I drew and then crossed out entirely because I realized halfway through sketching it that payments needed to reference invoices too, which meant a fifth relationship I hadn't accounted for going in. Showing that page to Dana later got a knowing laugh rather than surprise, since she'd apparently been through roughly the same exercise herself before I joined, just without writing it down.

## where this could change

If Ledgerline ever needed flexible per-organization custom fields on invoices — something Lotte has floated for larger customers — a jsonb column on the existing tables gets us most of that flexibility without abandoning the relational core.
