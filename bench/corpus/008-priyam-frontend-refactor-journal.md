2026-02-18. Spent most of today staring at the invoice editor component and admitting it's grown into something nobody wants to touch anymore. It started clean when we built it for the first demo, a single `InvoiceEditor.tsx` handling the line items table, the customer picker, the totals footer, and the draft-save logic all in one file. That was fine at four hundred lines. It is not fine at nineteen hundred lines, which is roughly where it sits today after four months of "just add one more prop" decisions that each felt reasonable in isolation. I counted fourteen `useState` calls in the top-level component this afternoon, several of which are derived values that should be `useMemo` instead, and at least three that duplicate state already living in the line items array. Kofi asked in standup why the editor felt laggy on invoices with more than thirty line items, and the honest answer is that every keystroke re-renders the entire component tree, totals footer included, because nothing is memoized and nothing is split apart. I'm giving myself the rest of the week to plan a real component split before touching any code.

## the plan

Talked it through with Dana over lunch since she's touched this component more than anyone besides me, mostly on the totals calculation side. The plan we landed on: split `InvoiceEditor` into a container that owns the draft state and four presentational children — `CustomerPicker`, `LineItemsTable`, `LineItemRow`, and `TotalsFooter` — with the draft state itself moved into a `useReducer` instead of the current scattered `useState` calls, since the actions are genuinely a small closed set: add line item, remove line item, update field, set customer, mark dirty. `LineItemRow` gets `React.memo` so editing one row doesn't re-render the other twenty-nine, which should solve Kofi's laggy-editor complaint directly. Dana pointed out that `total_cents` needs to stay computed from the line items array on every render rather than stored as its own state, since we got bitten by a stale-total bug in November where the footer showed a number that didn't match what actually got sent to the API on save, and duplicating derived state is exactly how that class of bug creeps back in no matter how careful you think you're being in the moment. We also agreed to keep the API shape for saving a draft completely untouched — this is a pure frontend refactor, the payload format going to `/invoices/:id/draft` doesn't change at all, so there's no coordination needed with the backend side and no risk of an API contract mismatch sneaking in through the refactor. I sketched the reducer's action types on paper before opening my editor, which felt old-fashioned but caught two edge cases — removing the last line item, and switching customers mid-edit — that I would have otherwise discovered halfway through writing the reducer itself.

## first attempt, reverted

Started today by trying to do the whole split in one branch and got about sixty percent through before realizing I'd broken the auto-save debounce somewhere in the shuffle — drafts stopped saving silently, no error, just nothing persisting, which I only caught because I refreshed the page mid-edit out of habit and lost ten minutes of fake test data. Reverted the whole branch rather than debug forward into a mess, annoying but the right call, and started over with tests first this time instead of code first.

## second attempt, this time with tests first

Wrote the reducer in isolation before touching any component, with a full Vitest suite covering every action type against a fixture draft with six line items, including the two edge cases from my paper sketch. That took the whole morning and felt slow compared to just diving into components, but paid off almost immediately: the removing-last-line-item case exposed a bug in my own reducer logic where the totals footer would try to render a division against zero line items and throw, which never would have shown up in manual testing unless I happened to click the delete button on the very last row during a demo, exactly the kind of thing that gets discovered live in front of a client instead of in CI. Fixed it by guarding the average-line-item-value calculation, which turned out to be dead code nobody actually uses in the UI anymore, so I deleted it entirely instead of just guarding it, which felt satisfying. Split out `LineItemRow` next and wired `React.memo` with a custom comparison function since the default shallow compare wasn't skipping renders the way I expected — the row was receiving a fresh `onUpdate` callback identity on every parent render because I'd defined it inline instead of wrapping it in `useCallback` at the container level, a classic memoization footgun I've fallen for before and apparently needed to fall for again. Once that was fixed, typing in a line item field on a forty-row test invoice went from visibly janky, maybe eight or nine frames dropped per keystroke by my rough eyeballing in the React DevTools profiler, to completely smooth. `CustomerPicker` and `TotalsFooter` were comparatively easy extractions once the reducer and the memoized row existed, mostly just moving JSX and updating prop names, maybe ninety minutes combined including the tests. ## mood

Tired but genuinely pleased with this one — the kind of refactor that's tedious in the middle but obviously worth it by the end, unlike some cleanups that just move complexity sideways without actually reducing it anywhere. Writing the reducer tests first felt slow this morning and paid for itself twice over by evening, a lesson worth trusting by default next time.
