# Setting Up Ledgerline Locally

This is the canonical setup guide for getting the Ledgerline monorepo running on your machine. It assumes you already have Node 20+, `pnpm`, and Docker installed. If you hit something this guide doesn't cover, please add it here rather than only asking in `#ledgerline-eng` — the next person will thank you. See also [[009-deploy-to-staging]] once local is working.

## Full walkthrough

Start by cloning the repository and installing dependencies from the root with `pnpm install`. This is a `pnpm` workspace, so a single install at the root pulls dependencies for `packages/api`, `packages/web`, and `packages/shared` together and links the shared package into both consumers automatically. Do not run `npm install` inside an individual package directory; it will create a duplicate `node_modules` tree and silently break the TypeScript project references that let the API import types from `shared` without a build step in between.

Once dependencies are installed, bring up Postgres with `docker compose up -d db`. The compose file defines a single `db` service on port 5432 with a persistent named volume, so data survives container restarts but not `docker compose down -v`. Copy `.env.example` to `.env` in `packages/api` and leave the defaults as-is unless you've changed the compose file yourself; the defaults point at the local container with a throwaway password that only exists in development. Never reuse that password anywhere real.

With Postgres running, apply migrations from `packages/api` with `pnpm db:migrate`. This runs every pending migration in `packages/api/migrations` in order using `node-pg-migrate`. If you ever need to start from a clean slate, `pnpm db:reset` drops and recreates the database before re-running every migration, which is the fastest way to recover from a bad local migration experiment without thinking too hard about what state you're in. After migrations succeed, seed some fake data with `pnpm db:seed`. The seed script creates one organization, a handful of customers, and a few invoices in various states — draft, sent, overdue, paid — so the frontend has something realistic to render without you creating everything by hand.

Now start the API with `pnpm --filter api dev`, which runs the Express server on port 4000 with `tsx watch` for automatic restarts on file changes. In a separate terminal, start the frontend with `pnpm --filter web dev`, which runs Vite on port 5173 and proxies `/api` requests to port 4000 so you never hit CORS issues locally. Open `http://localhost:5173` and you should see the login screen; the seed script prints a dev login (email and a fixed password) to the console the first time it runs, so scroll back in your terminal if you missed it.

A few things that trip people up. First, if TypeScript errors appear in your editor about missing types from `@ledgerline/shared`, restart the TS server in your editor rather than assuming the build is broken — VS Code in particular caches project references aggressively and doesn't always notice when `shared` changes. Second, if `pnpm db:migrate` fails with a connection error, check that the Postgres container actually finished starting; `docker compose logs db` should show `database system is ready to accept connections` before migrations will succeed, and there's currently no automatic retry wired into the migration script. Third, hot reload on the API occasionally misses changes to files that aren't directly imported by `index.ts` — if a change to a route handler doesn't seem to take effect, a manual restart of `pnpm --filter api dev` fixes it every time and is faster than debugging why.

Finally, run `pnpm test` from the root before pushing anything. It runs unit tests for both packages plus a handful of integration tests in `packages/api` that spin up a fresh test database on a separate port, so they won't clobber whatever you're using for manual testing in your dev environment.

## Verifying everything works

Before writing code, confirm the whole loop works end to end. Log in with the seeded dev account, create an invoice with a couple of line items, and confirm the total updates as you add each one. Mark it sent and check it shows up read-only, matching the immutable-invoice behavior in [[002-architecture-overview]]. If that works, you're ready for real tickets. If something breaks, it's almost always the API not running, a stale `.env`, or unfinished migrations.
