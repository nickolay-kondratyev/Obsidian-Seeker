Today marks the official kickoff of Ledgerline, and I wanted to write down where my head is at before the noise of daily standups and Linear tickets buries the reasoning. We spent most of last week arguing about stack choices, and I think we landed somewhere sensible: TypeScript across the board, Postgres for storage, a plain Express API instead of anything trendier. Kofi pushed hard for Postgres over a document store, and honestly it wasn't a hard sell once we thought seriously about what an invoicing app actually needs — foreign keys, transactions that must not partially apply, and the ability to run ad-hoc SQL reports for customers who ask "how much did I invoice last quarter." A document database would have made the easy things marginally easier and the important things much harder. I keep reminding myself that boring technology is a feature, not a compromise, especially with four people and no dedicated ops person. Priyam is less sure about React versus something lighter for the frontend, but given how much of the UI is forms — invoice line items, customer records, payment reconciliation — component reuse matters more than bundle size right now. Lotte, to her credit, stayed mostly out of the stack debate and just kept asking "will this let me ship the workflow I sketched," which is exactly the right question and one I should ask myself more often instead of getting pulled into architecture astronautics.

## What I worked on

I spent the morning scaffolding the repository: a `packages/api` and `packages/web` split inside one monorepo, sharing a `packages/shared` package for types like `InvoiceStatus` and `Money`. Getting the shared types working across both packages with proper TypeScript project references took longer than I'd like to admit — nearly two hours fighting `tsconfig` path resolution before I found the right combination of `composite` and `references` settings. In the afternoon I wrote the first migration: `organizations`, `users`, and a bare-bones `invoices` table with just `id`, `org_id`, `customer_name`, `total_cents`, and `status`. It's intentionally minimal; I don't want to guess at columns we don't need yet and then have to write cleanup migrations later. I also set up `node-pg-migrate` rather than writing raw SQL files by hand, mostly because rollback support matters once more than one person is touching the schema concurrently, and I don't trust us to remember to write down-migrations manually every time under sprint pressure. By the end of the day I had a working `POST /api/v1/invoices` endpoint that inserts a row and returns it, no validation yet beyond "the required fields exist," which is enough to unblock Priyam building the create-invoice form tomorrow. I pushed everything to a `kickoff` branch rather than `main` since none of it has been reviewed, and I want Kofi to look at the migration tooling setup specifically before we build on top of it. Tomorrow I want to add request validation with Zod and get basic auth scaffolded, even if it's just a hardcoded dev user for now, so Priyam isn't blocked waiting on real sessions. I also want to write a short `CONTRIBUTING.md` covering how to run migrations locally, since I already forgot my own `npm run db:migrate` command twice today and had to grep the `package.json` scripts, which is not a great sign for anyone joining later without the context baked into their head. Kofi mentioned he'd like a Docker Compose file for Postgres so nobody has to install it natively, which seems like an easy win I can knock out in twenty minutes once the core endpoint work settles down for the day.

## Blockers and open threads

The main thing nagging at me is the org-scoping question from [[002-architecture-overview]] — do we enforce isolation in application code, or lean on Postgres row-level security from day one. I lean toward starting with application-layer scoping because it's simpler to reason about and test right now, then adding RLS as a defense-in-depth layer once the query patterns stabilize. Kofi disagrees and thinks retrofitting RLS onto an app that wasn't built with it in mind is asking for trouble later, and I don't think either of us is wrong exactly. We agreed to timebox a real conversation about it before the schema gets much bigger, rather than let it linger as background anxiety for the next month. There's also a smaller open thread about whether `total_cents` should be computed from line items at read time or stored redundantly on the invoice row for query speed; I lean toward computing it for now since we have no evidence yet that it's a bottleneck, and premature denormalization tends to be the kind of thing that quietly rots once nobody remembers to keep both values in sync.

## Reflection

Day one felt good, if a little exhausting. There's a specific kind of energy in greenfield work, where every decision is still cheap to reverse, that I want to remember exists once we're six months in and everything feels load-bearing. I'm trying to resist the urge to build for imagined future scale and instead build the smallest thing that's honest about what Ledgerline needs today, trusting that a decent schema and clear boundaries between packages will make the inevitable pivots less painful than they'd otherwise be. I want to check back in on this entry in six months and see whether that instinct held up, or whether I quietly abandoned it the first time a deadline got tight and shortcuts started looking reasonable again.
