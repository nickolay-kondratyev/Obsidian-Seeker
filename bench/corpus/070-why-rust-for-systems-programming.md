I've been at this for a few months now, evenings and weekends, alongside the study group and a couple of small projects, and I keep noticing the same question surface whenever a session runs long or an exercise takes three tries instead of one: why this language specifically, out of everything I could be learning instead. I've dabbled in Go, poked at C++ during a systems class years ago, and written plenty of Python and JavaScript for work, so it's not that I lack alternatives. The honest answer, as best I can articulate it after enough hours to have a real opinion rather than secondhand enthusiasm, is that Rust is the first language that made the invisible costs of the systems I already build visible to me, and once you've seen those costs clearly it's hard to unsee them. Every web service I've shipped for work sits on top of a runtime making decisions about memory, concurrency, and layout that I never had to think about, and mostly that's fine, that's the whole point of a managed runtime doing its job well. But learning Rust seriously means learning the layer underneath that abstraction, the one Go, Python, and JavaScript all quietly manage on my behalf without asking permission. That's not a criticism of those languages, which are excellent at what they're built for and which I'll keep reaching for at work tomorrow. It's more that I wanted, for the first time in years, to actually understand what's happening underneath the abstraction rather than trusting it blindly the way I've trusted garbage collectors and dynamic typing for most of my career, and Rust turned out to be the vehicle that made that understanding accessible without raw C and segfaults every evening. The borrow checker, which I resented for the first several weeks, straddles exactly that line: it forces you to reason like a systems programmer about ownership, but catches mistakes at compile time instead of letting them become 2am production incidents, a rare combination of rigor and safety I haven't found packaged together quite this way anywhere else.

## The C comparison keeps coming up

Every conversation about "why Rust" eventually lands on a comparison to C, usually initiated by someone else, and I understand why even though it initially annoyed me as a lazy framing. C gives you the same proximity to memory and layout, the same absence of a garbage collector, the same mental model of what the machine does with your bytes, but none of the safety net. Rust's pitch, as far as I can tell after months of actually living inside it, is that you shouldn't have to trade memory safety for that proximity, that the compiler can statically prove the absence of bugs C leaves as the programmer's ongoing responsibility. Having felt this firsthand in that C class years ago, chasing a use-after-free bug for a weekend that Rust would have refused to build, the pitch lands.

## What still feels hard most weeks

I don't want this to read like uncomplicated praise, because plenty still feels genuinely hard most weeks, and pretending otherwise would be dishonest to both future-me and anyone reading this later for a realistic sense of the actual learning curve involved. Lifetimes remain the single biggest source of friction; I can usually make code compile through trial and error faster than I can explain confidently why my fix actually worked, which is a bad sign for how deep the understanding really goes underneath the passing build. The trait system, while genuinely elegant once it clicks, took real time to stop feeling like an obstacle course of unfamiliar syntax standing between me and code that should just work the way it obviously would in any language I already knew well. And I still reach for `.clone()` more than I'd like to admit whenever the borrow checker pushes back hard enough, which Dana correctly calls a crutch every single time she spots it in review, and she's right to keep calling it out even when it stings a little in the moment of getting unblocked.

## What surprised me after the first few months

The genuinely surprising part hasn't been the difficulty, which I expected walking in given the language's reputation preceding it everywhere I looked before starting. It's how much the discipline transfers back into code I write for work in languages with entirely different safety models and guarantees. I catch myself now thinking more carefully about ownership in Python code, about who actually holds a reference to a mutable list and whether some other part of the codebase might be quietly holding onto the same one, questions I used to wave away as "not really my problem in a garbage-collected language" without much further thought. The systems meetup reinforced this same lesson from a different angle entirely, see [[066-systems-meetup-notes]]: the talk on memory layout wasn't really about Rust specifically at all, it was about understanding what your data actually costs regardless of which language happens to be hiding those costs from you at any given moment in your career. That's a lesson that generalizes far past this one language, even if Rust is what finally forced me to sit still and actually learn it properly instead of continuing to wave it away. I also didn't expect the study group itself to matter as much as the language did; debugging the todo app's write-back bug alongside Dana, see [[063-borrow-checker-struggles]], taught me more about actually reading compiler output in twenty focused minutes of pairing than several tutorials had managed on their own across multiple prior attempts at learning this material solo.
