## Comparing project ideas

Four candidates came up between me, Dana, and Kofi over the last week, mostly in passing comments during the todo app pairing sessions rather than a real brainstorm. A grep clone feels like the natural next step after file I/O and error handling, since it touches string processing and command-line argument parsing without needing anything exotic. A tiny key-value store came up too, which would be a good excuse to learn about serialization and maybe a simple on-disk format, though it risks ballooning past a "small evening project" if we're not careful about scope from the very first session. Lotte floated a basic HTTP client wrapping `reqwest`, arguing it would connect more directly to work she does during the day, but Kofi pointed out async is explicitly out of scope for this phase of the group, which the reqwest approach would drag in almost immediately. A word-frequency counter also got mentioned as the simplest possible option, mostly by me, half-joking, as the fallback if everything else felt too ambitious for a group that's still shaky on lifetimes some weeks.

## First design pass

Assuming the grep clone gets picked, here's a rough shape before I forget the train of thought. Command line: `minigrep <pattern> <file>`, reading the whole file into a `String` for now rather than streaming line by line, since streaming is an obvious "version two" improvement once the basic version works end to end. Matching starts as plain substring search using `str::contains`, with a `--case-insensitive` flag added once the happy path works, mirroring almost exactly the structure the official book uses for its own minigrep chapter, which I'm deliberately not looking at too closely yet so the design still feels like mine rather than a transcription exercise. Error handling reuses the pattern from the todo app: a small enum for `FileNotFound` and `EmptyPattern`, propagated with `?` through `main`, since that pattern worked well enough there that reinventing it here would just be busywork for its own sake. Output goes straight to stdout, one matching line per row, with the matched substring left unhighlighted for version one; color highlighting is tempting but adds a dependency and a mode-detection problem, whether output is a real terminal or piped somewhere else, that feels like a distraction from the core lesson of the exercise. Tests will shell out to the built binary against a couple of fixture text files checked into the repo, following the same integration-test approach that caught the todo app's write-back bug before it shipped anywhere that mattered, which gives me some confidence the approach generalizes rather than being a one-off that happened to work for that specific project. I want to keep the file small enough that the whole thing fits in one sitting's worth of review, maybe two hundred lines including tests, so nobody in the group feels like they need a spare evening just to read the starting point before contributing anything themselves. Once the basic version works I'd like to add a `--line-number` flag as a small stretch goal, mostly because it forces me to think about tracking position while iterating rather than just matching, which feels like a natural next lesson once substring matching itself stops being interesting on its own.
