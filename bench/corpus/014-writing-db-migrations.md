Every schema change in Ledgerline goes through node-pg-migrate. No exceptions, not even for a "quick" column rename on a Tuesday afternoon. We learned this the hard way in January when someone ran an ad-hoc `ALTER TABLE` against staging and the migration history diverged from what production actually had, which took most of a morning to reconcile. See [[007-database-schema-doc]] for the current shape of the tables.

## How we write and review a migration

Start every migration with `pnpm --filter api migrate create <short-description>`, which drops a timestamped file into `packages/api/migrations/`. The name matters more than people expect: six months from now, whoever is reading `git log` on that directory needs to understand what happened without opening the file, so `add-invoice-revision-column` beats `fix-stuff` every single time. Resist the urge to batch three unrelated changes into one migration just because you happen to be touching the schema anyway — if the deploy needs to be rolled back, you want the blast radius to be as narrow as possible.

Always write the `down` migration, even when you're fairly sure nobody will ever run it. In practice we've had to roll back exactly twice in the project's history, both times within an hour of a staging deploy, and both times having a working `down` saved us from writing an emergency hotfix migration under pressure. If a migration genuinely can't be reversed cleanly — say, a data backfill that discards information — write the `down` as a no-op with a comment explaining why, rather than skipping it entirely. Reviewers should treat a missing `down` as a review blocker unless there's a documented reason.

Every migration that touches a table with existing production rows needs a plan for backfilling before we make a column `NOT NULL`. The pattern we've settled on: add the column nullable, ship it, backfill in a small batch job or a one-off script, confirm the backfill is complete with a count query, and only then ship a follow-up migration that adds the `NOT NULL` constraint. Doing all of that in one migration risks locking the table for however long the backfill takes, and on `ledger_entries`, which is already the largest table in the system, that lock could realistically run into minutes. Kofi has a standing rule that any migration touching `ledger_entries` or `invoices` gets tested against a copy of the staging dataset first, not just an empty local database, because row counts change the calculus on lock duration and index build time in ways that are easy to miss when your local dev database has forty rows in it.

Index creation deserves its own mention. `CREATE INDEX` takes a lock that blocks writes unless you use `CREATE INDEX CONCURRENTLY`, and node-pg-migrate needs to be told explicitly to run outside a transaction for that to work (`pgm.createIndex(..., { concurrently: true })` and setting the migration itself to non-transactional). Forgetting this on `invoices.org_id` in October caused a thirty-second write stall on staging that looked, for a few uncomfortable minutes, like a real outage before Dana traced it back to the migration that had just run.

We also require that every migration PR include the generated SQL in the description, not just a link to the TypeScript file, because reviewers catch far more issues reading raw SQL than reading the query-builder calls that produce it. Naming consistency matters too: columns storing money are always `_cents` suffixed bigints, timestamps are always `created_at`/`updated_at` in UTC, and foreign keys follow `<table_singular>_id`. Small stuff, but it's the kind of small stuff that keeps [[007-database-schema-doc]] readable as the schema grows past the point any one person holds it entirely in their head.

One more habit worth naming: we never let a migration's `up` and `down` drift apart silently. Every reviewer is expected to actually read both directions, not skim the `up` and assume the `down` mirrors it correctly, because we've seen a `down` migration that dropped the wrong column after a mid-review rename left the file out of sync. Running the full `up` then `down` then `up` cycle locally before opening the PR catches most of that class of mistake for free, and it's cheap enough that skipping it has never once been worth the time saved.

## Testing a migration before it ships

Run the migration against a local database seeded from the staging schema dump, not an empty one — this is the single change that's caught the most real problems, since lock behavior and constraint violations often only show up once there's actual data present. Time the migration too: anything over a few seconds against staging-sized tables gets flagged for a closer look before it goes anywhere near production, even if it passed cleanly in an empty local database moments earlier.
