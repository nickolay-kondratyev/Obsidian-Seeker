2026-04-02. Spent the morning digging into the `jobs` table because the dashboard's "send invoice reminder" emails have been landing later than they should, sometimes twenty minutes after the scheduled `run_after` time instead of within the minute or two we aim for. Pulled up staging and production side by side and found the worker loop is polling `jobs` every thirty seconds with a plain `SELECT ... WHERE status = 'pending' AND run_after <= now() ORDER BY run_after LIMIT 10`, which was fine back when we had maybe fifty jobs a day and is clearly not fine now that we're pushing closer to four thousand a day across all organizations. The query itself isn't slow in isolation, I checked with `EXPLAIN ANALYZE` and it's using the partial index fine, coming in under five milliseconds even against the full table. The actual problem is simpler and dumber than a query performance issue: we only ever process ten jobs per thirty-second tick, one worker process, no concurrency at all, so once the queue depth crosses a few hundred pending jobs during a busy morning, jobs just back up in a straightforward FIFO-ish queue with a badly undersized drain rate relative to the arrival rate. I should have caught this from metrics alone — we do have a `jobs_pending_count` gauge, but nobody's been watching it closely enough to notice the trend creeping up over the last six weeks. Feels like a classic case of a number quietly getting worse in small increments each week that no single day looked alarming.

## what I'm going to do about it

Talked this through with Dana at lunch since she wrote the original job-queue implementation back when [[007-database-schema-doc]] first got the `jobs` table added, and we agreed the honest fix here isn't reaching for Redis or a real broker yet — that's a bigger infrastructure change than the actual problem calls for right now, and we specifically chose not to add that dependency at launch, a decision I still think was right for where we were then. Instead: bump the worker to pull fifty jobs per tick instead of ten, and run three worker processes instead of one, each claiming jobs with a `FOR UPDATE SKIP LOCKED` clause so they don't step on each other's claims, which Postgres supports natively and which I should have just done from day one instead of the naive single-worker loop I originally wrote under deadline pressure before the first client demo. Did some rough back-of-envelope math: at fifty jobs per tick times three workers times two ticks a minute, that's a theoretical ceiling of three hundred jobs a minute, comfortably above our current peak arrival rate of maybe forty a minute during the worst part of the morning rush, with plenty of headroom for the recurring-invoices feature on the [[012-roadmap-q2]] roadmap that's going to add a meaningful new source of job volume once it ships. Also want to add proper alerting on `jobs_pending_count` crossing a threshold, say two hundred pending for more than five minutes straight, instead of relying on someone noticing complaints trickle in from account managers about late reminder emails, which is a genuinely bad way to find out about a systems problem and honestly a little embarrassing that it's how this one surfaced. Wrote up a short plan doc before touching any code, partly because Dana's migration-planning habit from the sprint retro notes has clearly rubbed off on the rest of us for the better, and partly because `FOR UPDATE SKIP LOCKED` behavior under concurrent load is exactly the kind of thing I want reviewed by a second set of eyes before it runs against production job processing, given how bad a subtly wrong locking change could get if two workers somehow double-processed the same reminder email to a real customer.

## afternoon: testing SKIP LOCKED locally

Spun up three worker processes against a local seeded queue of two thousand fake jobs to make sure the claiming logic actually behaves the way I expect under real concurrency rather than just trusting the Postgres docs on faith. First attempt had a bug where I forgot to wrap the select-and-update in a single transaction, so two workers occasionally did claim the same job in the tiny window between the select and the status update, exactly the race I was trying to avoid in the first place, which felt a little humbling given how confident I'd been walking into the test. Fixed it by moving both statements inside one `BEGIN`/`COMMIT` block with the `FOR UPDATE SKIP LOCKED` on the select, reran the same two-thousand-job test five times, zero duplicate claims across all five runs, and average end-to-end drain time dropped from what would have been over an hour at the old single-worker rate to under seven minutes for the full batch, which felt genuinely satisfying to watch tick down in the terminal.
