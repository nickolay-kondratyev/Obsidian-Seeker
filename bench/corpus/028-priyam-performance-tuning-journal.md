Spent the whole day chasing a slowness complaint from one of our launch customers, the landscaping business Lotte onboarded personally, whose invoice list view apparently takes several seconds to load once they've got more than a couple hundred invoices in their history. I'd been putting this off mentally as an edge case, since our seeded test data never has more than thirty invoices per organization and everything feels instant against that, but today it stopped being theoretical when the complaint landed in our support inbox with a screenshot of a loading spinner that had clearly been sitting there long enough to annoy someone running an actual business. I opened the production database, read-only through Kofi's reporting replica, and reproduced the slowness immediately: the invoice list endpoint was taking almost three seconds for that organization, against a target we'd always assumed without writing down, meaning comfortably under three hundred milliseconds for anything customer-facing. Three seconds makes someone wonder whether the product is broken, and I felt a specific embarrassment realizing we'd shipped something that degrades this badly under realistic usage.

## Finding where the time goes

I pulled up the query plan for the invoice list endpoint using `EXPLAIN ANALYZE` against the replica, something I honestly don't do often enough given how much of my day is spent on the frontend rather than close to the database, and the problem was obvious almost immediately once I actually looked. The endpoint joins `invoices` to `invoice_line_items` to compute each invoice's total on every single list request, rather than reading a precomputed total off the invoice row, and that join was doing a full sequential scan across `invoice_line_items` for the organization instead of using an index, because there was no index on `invoice_line_items.invoice_id` at all — an oversight from the earliest schema work described in [[003-dana-dev-journal-kickoff]], back when nobody was thinking about query performance because there was no real data to make it visible yet. Two hundred invoices with an average of four line items each is only eight hundred rows, which sounds trivially small, but a sequential scan repeated once per invoice inside a loop-style join plan turns into a genuinely bad access pattern that gets dramatically worse as the row count climbs, and this customer's history is only going to keep growing from here, not shrink back down. I also noticed the endpoint was fetching every invoice field including notes and internal metadata even though the list view only renders four columns, which wastes bandwidth and serialization time but wasn't the dominant cost here; the missing index was clearly doing almost all of the damage on its own, and I wanted to fix the real bottleneck rather than spend the afternoon polishing a secondary cost that barely mattered by comparison.

## The fix

Added a straightforward index on `invoice_line_items.invoice_id` via a new migration, plus a narrower `SELECT` on the list endpoint that only pulls the columns the UI actually renders. Kept the fix small and boring rather than reaching for caching or denormalizing the total onto the invoice row, since an index alone should close nearly the entire gap here, and anything heavier felt premature before proving the simple thing insufficient first. Wrote it as one focused, reversible change, nothing else bundled in.

## Verifying it actually worked

Ran the same `EXPLAIN ANALYZE` against the replica after applying the migration there first, and the plan flipped from a sequential scan to an index scan immediately, exactly as expected once the missing index existed for the planner to actually use. Query time for that same customer's two hundred and thirty invoices dropped from just under three seconds to about forty milliseconds, close enough to instant that I ran it three separate times to make sure I hadn't made a mistake measuring, since an improvement that dramatic felt almost too clean to trust on a first read. Deployed the migration to production during a quiet window this evening after confirming with Kofi that adding an index on a table this size wouldn't lock writes for long enough to matter, and it applied in under a second with no visible impact on anything else running against the database at the time. I also went back through our other list endpoints — customers, payments, and the ledger reconciliation view Kofi built last month — checking for the same missing-index pattern before calling it done for the day, since if this oversight snuck into the invoice table it was entirely plausible it existed elsewhere too, and I'd rather find those proactively during one focused afternoon than get three more separate support tickets over the coming months, one per endpoint, each requiring its own investigation from scratch and its own apologetic message to whichever customer noticed first. I found one more instance on the payments list, fixed it the same way, and left the customers endpoint alone since it already had the right index from an earlier migration nobody documented clearly, though I added a comment explaining why so the next person doesn't waste an afternoon rediscovering it from scratch the way I nearly did today. Filed a small ticket to check the recurring-invoice job path too, since it queries similarly and I ran out of hours before verifying it directly myself.

## What I'm taking from this

We need production-scale seed data in staging, not a lightweight demo dataset, because this class of bug is completely invisible against thirty rows and only shows up under realistic volume.
