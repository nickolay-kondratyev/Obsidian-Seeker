# Lessons from a year of multi-tenant SaaS

Ledgerline is a year old now and still runs on a shared-schema multi-tenant model: one Postgres database, one set of tables, every row scoped by `org_id` at the application layer. No schema-per-tenant, no database-per-tenant, no row-level security yet either — just an `org_id` column and discipline. That last word is doing a lot of work in that sentence, and this article is mostly about what "discipline" actually costs in practice once real customers and real data are involved, because it looks cheap on a whiteboard and gets expensive fast in code review.

The appeal of shared-schema multi-tenancy is obvious at the start: one database to operate, one migration to run, one connection pool to size, one set of indexes to tune. Compared to database-per-tenant, which would mean provisioning infrastructure per customer and running migrations across dozens or eventually hundreds of databases in lockstep, shared-schema felt like the only sane choice for a four-person team with no dedicated ops headcount. That choice hasn't changed, and I'd make it again. What has changed is my confidence that "just filter by org_id" is a small detail rather than the central architectural risk of the whole system.

Every single query that touches tenant data needs an `org_id` filter, and there is currently no mechanism forcing that to be true other than a reviewer noticing its absence in review. We've caught two near-misses this year — both times a new list endpoint that would have returned every org's rows, not just the caller's. Neither shipped, because [[029-pr-review-guide]] calls out org scoping as a required check, but "we caught it in review" is a process guarantee, not a database one, and it degrades under deadline pressure. That gap is the single biggest thing I'd flag to a team starting a multi-tenant product today: decide early whether to enforce isolation at the database layer or the application layer — retrofitting the former onto a year of the latter is a real project, not a config flag, see [[010-why-postgres-not-mongo]].

The rest of this piece is the smaller lessons that only became visible with a year of real usage: indexing strategy, migration discipline, and the surprisingly large cost of "just add a column."

## Indexing has to assume org_id is in every query

Nearly every index in the schema now leads with `org_id` as the first column, because Postgres can only use an index efficiently when the query's filter matches its leading columns, and every real query filters by org first. This wasn't obvious on day one when the data was small enough that sequential scans were invisible in query time; it became obvious around month six when `invoices` and `ledger_entries` grew large enough that a missing `org_id`-leading index turned a ten-millisecond query into a multi-second one under load. We now treat "does this index lead with org_id" as a default schema-review question, because retrofitting an index onto a table already large enough to hurt means a concurrent build with real wall-clock time, not the instant operation it would've been on day one.

## Migrations get riskier, not safer, as tenants accumulate

A migration that's harmless against an empty table becomes a locking hazard against a table with a year of accumulated rows across dozens of orgs. [[014-writing-db-migrations]] covers the mechanics of how we handle this now — nullable-first backfills, concurrent index builds — but the lesson underneath the mechanics is that migration risk scales with tenant count in a way that isn't obvious until you've lived through a slow migration on a table you assumed was still small. Early on, every migration ran against a local database with a handful of seed rows, so lock duration and rewrite cost were effectively invisible; a rewrite that takes milliseconds against ten rows can take noticeable seconds or minutes against millions of rows once enough tenants have onboarded, and testing against a realistically sized dataset is the only way to catch that ahead of time. We didn't internalize this until a migration that looked routine in review turned into a multi-minute write lock on `invoices` in staging, a lucky place to learn that lesson rather than in production during business hours.

## "Just add a column" stops being free

Every new column on a shared table is now a column every tenant carries whether they use the feature or not, and every query against that table potentially touches it. A column that seemed like a two-line migration for one customer's edge case turns into a permanent tax on every other tenant's query plan, which changes how casually we say yes to one-off customer requests that used to feel harmless. Early on, adding a column felt like the cheapest possible request to grant — a nullable text field for one customer's odd invoicing preference seemed practically free compared to building a whole configuration system for something only one org cared about. What we didn't account for is that the column doesn't stay scoped to that one customer's mental model; every future engineer reading the `invoices` table has to understand what that column means, whether it's populated, and whether their query needs to account for it, even if they're working on a feature for a completely unrelated tenant. Multiply that by a year of similar one-off requests and the table accumulates a kind of sediment — columns nobody quite remembers the justification for, that show up in every query plan and every schema diagram regardless of relevance. We've started pushing back harder on schema changes that exist to serve a single customer, preferring a `settings` JSON column for genuinely one-off preferences over a dedicated typed column, even though it trades some query performance and type safety for containment.

## What I'd tell a team starting today

Decide on tenant isolation strategy — application-layer filtering versus row-level security — before writing the first query, not a year in. Retrofitting is possible, but it's real work, and every month of delay adds more code to touch.
