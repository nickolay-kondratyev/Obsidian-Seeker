This document lays out how we test Ledgerline, written after months of ad-hoc test-writing left uneven coverage — some routes tested thoroughly, others barely at all. The goal isn't perfect coverage, it's confidence that money math and invoice state transitions can't silently break, since those are the bug categories that would actually hurt a customer's business. Everything else gets tested proportionally to how often it changes, not according to an abstract coverage target. See [[007-database-schema-doc]] for the schema these tests exercise.

## Unit tests

Unit tests live beside the code they test, `*.test.ts` files colocated with their source, run with Vitest across both `packages/api` and `packages/web`. These cover pure functions: money arithmetic, invoice status transitions, date formatting per organization timezone, and the Zod validation schemas for every API input. We deliberately keep these fast and hermetic — no database, no network, no filesystem — so the full unit suite runs in under four seconds locally and in CI, which matters because Dana and Kofi both run it on every save via watch mode, and a slow suite would quietly stop being run. Every bug fix in these categories gets a regression test in the same commit as the fix, no exceptions, because we've been burned twice already by the same rounding bug resurfacing six weeks apart once we stopped enforcing this.

## Integration tests

Integration tests spin up a real Postgres database on a dedicated test port, run all migrations, and hit actual API routes through Express rather than mocking the database layer. These are slower — the full suite takes about ninety seconds — but they're what actually caught the `ledger_entries` migration ordering issue during the March sprint, described in [[006-sprint-retro-march]], before it reached staging. We test the full lifecycle of an invoice here: create as draft, add line items, send, confirm it becomes read-only, and confirm a new revision is created on edit rather than the original row changing. Payment reconciliation and the recurring-invoice job also get integration coverage since both involve multiple tables changing together inside a transaction, and unit tests alone can't catch a bug in how those transactions are composed or where they might partially commit. We reset the test database between test files rather than between individual tests, which is a deliberate speed tradeoff — tests within a file are written to avoid interfering with each other's rows through unique customer and organization names per test.

## What we don't test yet

There's no end-to-end browser testing at all — no Playwright, no Cypress — a known gap the team has deliberately deferred rather than forgotten about. Manual click-through before release has caught real issues at acceptable cost so far, though Kofi expects that to stop scaling once multi-currency invoices land. Email delivery is also untested beyond a mock transport, and load testing doesn't exist yet either.

## Running tests and closing the gaps

Run `pnpm test` from the repo root to run everything, or `pnpm test:unit` and `pnpm test:integration` separately for faster feedback. Integration tests require Postgres running via `docker compose up -d db` first, same as local development in [[004-local-dev-setup]]. CI runs both suites on every pull request and blocks merging on failure; nobody has override permissions on that gate. The team agrees the biggest remaining gap is the job queue: recurring invoice generation and reminders are tested for the happy path, but retry behavior when a job throws partway through has essentially no coverage. Kofi opened a ticket to address this next quarter, tied to the question in [[002-architecture-overview]] about whether the `jobs` table will keep scaling. Priyam wants smoke-level browser tests for invoice creation, the single most business-critical path.
