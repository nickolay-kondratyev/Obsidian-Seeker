I keep forgetting the exact sequence for turning a raw GTFS zip into something I can actually query for headways, so this is the reference version. It assumes the feed is a standard static GTFS export from a transit agency, not a real-time feed, and that I'm working locally rather than in a notebook server, since the agency I'm studying doesn't publish real-time data anyway.

## Loading and Querying the Feed

Start by downloading the agency's GTFS zip from their developer page or open-data portal and unzipping it into a working folder. A standard feed contains `stops.txt`, `routes.txt`, `trips.txt`, `stop_times.txt`, `calendar.txt`, and usually `shapes.txt` and `calendar_dates.txt` for exceptions. The files are plain CSVs, so the fastest way to get moving is loading them straight into a local SQLite database rather than wrangling them in a spreadsheet, which chokes on anything past a few hundred thousand rows. I load each CSV as its own table, keeping the original column names so I don't have to cross-reference the spec every time I write a query. `stop_times.txt` is almost always the largest file by far, sometimes tens of millions of rows for a mid-size agency, so I index it on `trip_id` and `stop_id` immediately after loading, otherwise every join against it crawls.

Once the tables are in, the first sanity check is always the same: count trips per route per service_id in `calendar.txt`, and eyeball whether weekday service actually looks different from weekend service. I got burned once assuming a small agency's calendar had separate Saturday and Sunday patterns when they'd collapsed everything into a single weekend service_id, and my headway numbers were quietly wrong for two weeks before I noticed the mismatch against my field observations. Cross-checking against `calendar_dates.txt` matters too, since holiday exceptions and seasonal service changes live there instead of in the base calendar, and a lot of agencies use exception-only calendars where the base `calendar.txt` row is nearly empty and everything is defined through additions and removals in the exceptions file.

For headways specifically, the core query joins `stop_times` to `trips` to `routes`, filters to the service_id and stop_id I care about, orders by `arrival_time`, and computes the difference between consecutive arrivals at that stop for that route and direction. GTFS times can exceed 24:00:00 for trips that run past midnight, which trips up naive time parsing if you're not expecting it, so I convert everything to seconds-since-midnight rather than trying to use a real time type. I usually compute headways separately for AM peak, midday, PM peak, and evening windows, since averaging across the whole service day hides exactly the peak-to-off-peak contrast that matters for a walkshed or frequent-network analysis. It's also worth computing headway variability, not just the mean, because a route that averages twelve minutes but bunches into pairs feels a lot less frequent to a rider than a genuinely even twelve-minute service.

The other thing worth doing early is mapping `route_type` values to something readable, since the spec uses integer codes (0 for light rail, 1 for subway, 3 for bus, and so on) that are easy to misremember. I keep a small lookup table for this rather than hardcoding the mapping into every query, since I end up rewriting the same case statement across five different scripts otherwise. Once headways are computed per stop and time window, I export the results to a CSV and bring them into QGIS or R for the mapping and statistical work, since SQLite is good for the extraction step but not for anything past that stage of the pipeline.

One last wrinkle worth flagging: `stop_times.txt` sometimes omits `arrival_time` and `departure_time` for intermediate timepoints on longer routes, leaving them blank and expecting interpolation between the nearest known stops. If you don't handle this, any headway query touching those stops silently returns nothing rather than an error, which is a much sneakier failure mode than a crash. I now run a quick coverage check after loading — counting how many `stop_times` rows have null times per route — before trusting any headway numbers downstream, since I've seen this affect a meaningful share of stops on routes serving the parts of the city I actually care about for the thesis.
